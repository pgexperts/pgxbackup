# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

This is `pgexperts/pgxbackup`, a snapshot/fork of upstream `pgbackrest/pgbackrest`. The upstream project has been **declared obsolete** (see README "Notice of Obsolescence") and is no longer maintained. This fork lives on a single branch (`eol`); there is no `main` or `integration` branch despite what `CONTRIBUTING.md` says about PR base branches. Treat this repository as archival unless the user states otherwise.

## Build

The project uses **meson + ninja** (not autotools, not cmake), C99, with unity builds enabled by default.

```
meson setup build              # configure once
ninja -C build                 # incremental build → build/src/pgbackrest
ninja -C build -j N            # parallel
```

Optional features (auto-detected, controllable via `meson_options.txt`):
- `libssh2` — SFTP storage support
- `libzstd` — Zstandard compression

`meson_options.txt` also exposes `configdir` (default `/etc/pgbackrest`) and `fatal-errors` (stop on first warning-as-error).

## Tests, formatting, and code generation

Everything goes through the Perl harness at `test/test.pl` — including code generation, valgrind, coverage, uncrustify, and Docker-based VM tests. There is no `pytest`/`make test`; do not look for one.

```
test/test.pl --dry-run                         # list every test
test/test.pl --module=common --test=wait       # run one test, native
test/test.pl --module=common --test=wait --vm-out --no-cleanup  # show output, keep test/test-0/ for inspection
test/test.pl --module=postgres                 # run a whole module
test/test.pl --vm=u22 --module=command --test=check  # run inside Docker container (vm codes: u22, rh8, d11, f43, a321, etc.)
test/test.pl --vm-build --vm=u22               # build the test container image
test/test.pl --gen-only                        # regenerate *.auto.c.inc / *.auto.h without running tests
test/test.pl --build-only                      # build pgbackrest binary into test/bin/<vm>/pgbackrest
test/test.pl --code-format                     # apply uncrustify formatting (CI's `code-format` job)
```

Coverage is required to be 100% for files listed under `coverage:` in `test/define.yaml`. A failing coverage report lands at `test/result/coverage.html`.

`define.yaml` is the source of truth for what tests exist, how many runs each contains, what files they cover, what harness/shim modules they need, and whether they require a container.

## High-level architecture

`src/main.c` wires up storage helpers (S3, GCS, Azure, CIFS, SFTP), error handlers, and a TRY block, then dispatches to a command handler in `src/command/<name>/`. The bulk of the program is organized into a few cooperating layers:

- **`src/command/`** — top-level commands (`backup`, `restore`, `archive-push`, `archive-get`, `expire`, `verify`, `info`, `check`, `stanza-create/upgrade/delete`, `repo` ls/get/put/rm, `server`, `local`, `remote`). `local` and `remote` are not user-facing — they are spawned worker processes; see protocol layer below.
- **`src/protocol/`** — custom binary protocol that lets `pgbackrest` talk to spawned local workers (parallel jobs on the same host) and remote workers (over SSH or TLS). `protocol/parallel.c` is the parallel job dispatcher; everything CPU-bound (compression, encryption, checksumming) goes through it.
- **`src/config/`** — option parsing and configuration model. `config.auto.h` and `parse.auto.c.inc` are **autogenerated** from `src/build/config/config.yaml`; do not edit them by hand.
- **`src/storage/`** — pluggable storage backends behind a common `Storage *` interface. Backends: `posix`, `s3`, `gcs`, `azure`, `cifs`, `sftp`, `remote` (proxied via the protocol layer). Each backend implements `read`, `write`, `storage` (path/info/list ops); some also have `helper.c` for backend selection.
- **`src/info/`** — manifest and info file (`backup.info`, `archive.info`, `backup.manifest`) read/write/checksum.
- **`src/db/`** — PostgreSQL client (libpq wrapper) and the cross-process protocol that proxies queries through a remote worker so the main host doesn't need direct DB access.
- **`src/postgres/`** — version-aware PostgreSQL interface. `version.auto.h` and `interface.auto.c.inc` are **autogenerated** from `src/build/postgres/postgres.yaml`.
- **`src/common/`** — foundational utilities: memory contexts, custom error/logging, custom string/list/keyValue/variant types, IO filters (compression, encryption, hashing) composable into pipelines, sockets, TLS, HTTP client, regex, time, fork helpers.

### Code generation pipeline

`src/build/` is a *separate* executable (`build-code`) that meson compiles first. It reads:

- `src/build/config/config.yaml` → `src/config/config.auto.h`, `src/config/parse.auto.c.inc`
- `src/build/help/help.xml` → `src/command/help/help.auto.c.inc`
- `src/build/error/error.yaml` → `src/common/error/error.auto.h`, `src/common/error/error.auto.c.inc`
- `src/build/postgres/postgres.yaml` → `src/postgres/version.auto.h`, `src/postgres/interface.auto.c.inc`

Regenerate via `test/test.pl --gen-only`. Never edit the `*.auto.*` files.

### Adding a configuration option

Two files must be touched (per `CONTRIBUTING.md`):

1. `src/build/config/config.yaml` — defines the option (type, commands, default, allow-list, indexed group, role)
2. `src/build/help/help.xml` — required `<summary>`, `<text>`, `<example>` (build fails if missing)

Then run `test/test.pl --module=command --test=help` to verify, and `test/test.pl --build-only` to produce a binary you can inspect with `test/bin/none/pgbackrest help <cmd> <option>`.

## Object & memory conventions

These are project-wide and pervasive — internalize them before editing any C file:

- **Object pointer is always `this`.** Constructors are `xxxNew()`, destructors `xxxFree()` (never `Create`/`Destroy`). Use `Begin`/`End` not `Start`/`Finish`.
- **Public fields go in a `XxxPub` struct** that must be the **first member** of the private `struct Xxx`. Header exposes inline getters via the `THIS_PUB(Xxx)` macro (which also null-checks `this`). Setters get a `Set` suffix; getters do not.
- **Long-lived objects are allocated inside `OBJ_NEW_BEGIN(Xxx) { ... } OBJ_NEW_END()`**, which creates a named memory context owned by the object. Function-scoped allocations go inside `MEM_CONTEXT_TEMP_BEGIN() { ... } MEM_CONTEXT_TEMP_END()` and everything inside is freed on exit. To return a value out of a temp context, switch into the caller's context with `MEM_CONTEXT_PRIOR_BEGIN()` and copy/dup there.
- **Every non-trivial function opens with `FUNCTION_LOG_BEGIN(level)` / `FUNCTION_TEST_BEGIN()`** and closes with `FUNCTION_LOG_RETURN(...)` / `FUNCTION_TEST_RETURN(...)`. `FUNCTION_LOG_*` survives in production builds; `FUNCTION_TEST_*` is compiled out. Use `FUNCTION_TEST_PARAM` for secrets so they don't leak into production logs.
- **User-facing logging:** `LOG_INFO`, `LOG_WARN`, `LOG_DETAIL`, etc., plus `_FMT` variants. Errors are thrown with `THROW_*` (defined in `src/common/error/error.h`). Hint messages start with `HINT:`; warnings/errors are lowercase except for proper nouns.
- **Variadic functions are an exception to the macro-naming rule.** They use lowercase macro names like `storagePathCreateP(this, path, .errorOnExists = true)` that expand to a struct-literal call.

## Coding-standard quick reference

Full rules are in `CODING.md`. Highlights that catch newcomers:

- 4 spaces, no tabs (except files that require them like Makefiles).
- 132-char hard line limit. Break **after the first function paren**, or after a complete conditional clause — not mid-expression.
- Inline comments start at column 69. `#define` constant values align at column 69. Macro continuation backslashes align at column 132.
- camelCase variables (lowercase first letter, no `i`/`j` for loop indices — use `nameIdx`), CamelCase types/enums (uppercase first letter), `UPPER_SNAKE` for `#define`. Trailing comma on the last enum element to minimize diff churn.
- Prefer `int`/`unsigned int` and the typedefs in `common/type.h` over exotic types.
- Prefer enums to integer `#define` constants. Prefer functions to macros (macros hurt coverage measurement).
- Braces are omitted for single-line `if`/`while` bodies; required when either the control or body spans multiple lines, and for `switch` cases that contain multiple statements or comments.
- **Comments for `extern` functions go in the `.h` file**; comments for `static` functions and implementation notes go in the `.c` file.
- Mark genuinely untestable code with `// {uncoverable - reason}` and untested code with `// {uncovered - reason}`. These are rare outside `common/` and test harnesses.

## Test harness conventions

- Test files mirror source paths: `src/command/expire.c` → `test/src/module/command/expireTest.c`.
- Each `testBegin("functionName()")` block is one "run" inside the test; `TEST_TITLE("...")` introduces a sub-test.
- Set up command options with `hrnCfgArgRawZ()` / `hrnCfgArgKeyRawZ()` and `HRN_CFG_LOAD(cfgCmdXxx, argList)` (see `test/src/common/harnessConfig.h`).
- Stage repo/storage state with `HRN_STORAGE_PUT*` / `HRN_INFO_PUT`; assert with `TEST_STORAGE_GET` (see `test/src/common/harnessStorage.h`).
- Assert results with `TEST_RESULT_STR`, `TEST_RESULT_UINT`, `TEST_RESULT_BOOL`, `TEST_RESULT_PTR`, `TEST_RESULT_VOID`, `TEST_ERROR` / `TEST_ERROR_FMT`. Reserve `HRN_*` macros for setup/teardown only; never use them to assert.
- If the code under test logs anything via `LOG_*`, the test must consume the log line with `TEST_RESULT_LOG()` / `TEST_RESULT_LOG_FMT()` before the run ends or the harness will fail.
- Multi-process tests use `HRN_FORK_BEGIN()` / `HRN_FORK_CHILD_BEGIN()` / `HRN_FORK_PARENT_BEGIN()` (see `test/src/common/harnessFork.h`).
- A libpq shim (`HRN_PQ_SCRIPT_SET` in `test/src/common/harnessPq.h`) lets tests stub PostgreSQL responses without a real server.
